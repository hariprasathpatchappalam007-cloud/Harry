02 / the measurement trap

A connection, a request and a session are different things.

MetricMeaningCan IIS provide it?
Concurrent connectionsOpen network connections, including idle keep-alive connections. HTTP/2 can multiplex multiple requests on one connection.Yes, site counters; not a user or session count.
Concurrent requestsRequests in flight at a particular instant. Queueing and execution are separate stages.IIS worker-request snapshots and runtime/queue counters; brief peaks can be missed.
Distinct users observedIdentities present in requests during a defined UTC window.W3C cs-username for supported authentication, or an approved application-written identity field. Not proof that users are still logged in.
Application / ASP.NET sessionsApplication-managed state, often shared by tabs in the same browser profile. A session can exist before login.Classic ASP.NET may expose aggregate Sessions Active; no generic per-user enumeration.
Authenticated login sessions per userUnexpired, non-revoked application login records for one identity; definition depends on the application's authentication model.Requires application/session registry telemetry. IIS cannot infer it reliably.
Direct answer: there is no universal PowerShell command that extracts every user's current login sessions from IIS. The supplied script counts observed activity from IIS logs and, when provided a complete application-owned session snapshot, counts active sessions per user at a chosen timestamp. It does not pretend one is the other.
  • Do not group sessions by client IP. NAT, proxies and Citrix SNIP addresses can combine many users; one user may use several IPs.
  • Do not count browser tabs, TCP connections, requests or cookies as logins. Several tabs usually share a session; separate browser profiles/devices may not.
  • Forms authentication often leaves cs-username as -. Application identity must then be emitted through approved instrumentation. Anonymous is unknown identity, not zero users.
  • Cross-node totals must be deduplicated centrally. A single session can appear on both nodes; local distinct counts cannot simply be added.

Session-state and load-balancer checks that are easy to miss

  • InProc state is worker-local. Non-sticky routing, recycling or multiple workers in one pool can lose or split state. Verify architecture before changing affinity or increasing maxProcesses.
  • Shared StateServer / SQL / distributed caches are not automatically healthy. Compare endpoint configuration, access, latency, expiry and serialization errors; never copy connection-string secrets into reports.
  • Cross-node authentication parity matters. Compare protected key sharing and application identity settings appropriate to the framework; mismatches can cause login loops and repeated sessions.
  • Health checks should reflect useful service readiness. A TCP listener or static page can be healthy while the application cannot serve requests. Validate what the deployed Citrix configuration actually supports; plan a safe alternative if constrained.
  • Do not blindly retry non-idempotent operations. A failed response does not prove that the backend performed no work. Use application-supported idempotency before enabling retries for transactions.
06 / ready-to-run PowerShell

Collect evidence without changing IIS settings.

Get-IISUserActivity.ps1 supports offline W3C analysis, application-session snapshots and optional local live IIS collection. It creates a unique subfolder for each run. It does not recycle pools, change limits, enable tracing, query SQL or call Citrix APIs.

Prerequisites: Windows PowerShell 5.1. The inventory lists Windows Server 2012, whose default PowerShell may be older: check $PSVersionTable.PSVersion and use an organization-approved management framework/runtime. Offline analysis can run on a separate approved workstation. Live collection requires elevated, 64-bit PowerShell, IIS management scripting components (Microsoft.Web.Administration) and the Request Monitor role service for worker-request inspection. Follow signing/execution policy; do not bypass it.

A. One user's activity from IIS logs

# Replace the site ID, log path, username and incident window.
# IIS W3C timestamps are UTC. 14:00 at UTC+05:30 = 08:30Z.
.\Get-IISUserActivity.ps1 `
  -LogPath 'D:\IISLogs\W3SVC1\u_ex261027.log' `
  -StartUtc '2026-10-27T08:30:00Z' `
  -EndUtc '2026-10-27T09:00:00Z' `
  -NodeName 'APP-NODE-A' `
  -UserName 'DOMAIN\alice' `
  -OutputDirectory 'D:\Restricted\IIS-Incident'

Omit -UserName to report all identified users. This filter affects the user/session reports only; status and minute reports retain all requests for incident diagnosis. Values are matched case-insensitively as they appear in the logs. Start is inclusive; end is exclusive. Supply explicit timestamps with Z or an offset.

B. Local live collection on each IIS node

# Run locally on EACH node during the problem, in elevated PowerShell.
# Use the same historical log window, but a separate node label.
.\Get-IISUserActivity.ps1 `
  -CollectLiveIIS -SiteName 'YOUR IIS SITE NAME' `
  -StartUtc '2026-10-27T08:30:00Z' `
  -EndUtc '2026-10-27T09:00:00Z' `
  -Samples 12 -IntervalSeconds 5 `
  -OutputDirectory 'D:\Restricted\IIS-Incident'

Auto-discovery uses recent files in the standard per-site W3C folder and default HTTPERR location. Override with -LogPath and -HttpErrPath for redirected/copied logs. Centralized, binary or non-file logging requires an appropriate W3C export. Twelve samples with five-second sleeps span at least 55 seconds, plus collection overhead and counter probing; they are not an exact fixed-rate trace.

Live samples are always collected now, even if the historical log window is earlier. Counters may be unavailable because of localization, absent runtime/categories, idle workers or permissions: read the warnings. Request snapshots use the documented IIS WorkerProcess.GetRequests API. If worker inspection fails, the request count is left unknown instead of reporting a false zero. Worker samples are sequential, not an atomic server-wide snapshot.

C. Optional pseudonymous session observation in custom W3C logs

# Only if the application ALREADY emits approved identity and hash fields.
.\Get-IISUserActivity.ps1 `
  -LogPath 'D:\IISLogs\W3SVC1\u_ex261027.log' `
  -UserField 'app-user-id' -SessionHashField 'app-session-hash' `
  -StartUtc '2026-10-27T08:30:00Z' -EndUtc '2026-10-27T09:00:00Z'

The hash field must contain a dedicated 64-hex SHA-256/HMAC-SHA-256 pseudonym, not cs(Cookie) or a raw session token. Use an application-side, approved keyed HMAC with a protected stable key where possible; preserve a consistent key across nodes for correlation. Logging instrumentation is an application change and is not performed by the script. Historical distinct session hashes are still not current logins.

Operational and privacy controls: pre-create an access-restricted output parent folder; the script inherits its ACLs and does not harden them. 07 / how to get actual sessions per user

The application must supply the user-to-session mapping.

Agree first whether "session" means an authenticated login, a classic ASP.NET state session or a vendor license seat. For login counts, ask the application team for a complete, consistent snapshot from its authoritative registry covering both nodes and this application. IIS, quser and Get-PSSession cannot provide this mapping; the latter tools refer to Windows/remote-management sessions.

  -UserName 'DOMAIN\alice' `

# Expected in application-sessions.csv for the sample above:
# User = DOMAIN\alice; ActiveSessions = 2; AsOf = 09:00:00Z
Counting rule at EndUtc: LastSeenUtc <= EndUtc, ExpiresUtc > EndUtc, and IsRevoked = false. Expiry must represent the application's effective idle/absolute timeout and account invalidation policy. Active means valid according to the registry, not necessarily a person interacting at this instant. Duplicate session hashes cause a hard failure instead of inflated totals.

If no registry exists

  1. Instrument login/session creation and authenticated request completion using a stable user ID, safe session pseudonym, UTC timestamps, node/app identity, effective expiry and lifecycle state.
  2. Maintain a central record with defined idle timeout, absolute expiry, logout/revocation, session rotation and app-restart behavior. Update on activity according to the application's real expiry rules.
  3. Do not rely only on Session_End: classic ASP.NET supports that event only for InProc, and process termination can prevent reliable cleanup. Use expiry and authoritative invalidation, not event delivery alone.
  4. Export a consistent snapshot at the chosen analysis time. A present-day snapshot cannot reconstruct an old incident after expiry/rotation; retain approved lifecycle history for historical RCA.
  5. For stateless tokens, exact login counts require an explicit login/token registry. The number of valid tokens is not automatically the number of people or devices.

Per-user concurrency is a separate instrument. Record request-start and completion events with user/session pseudonyms and a correlation ID, then calculate overlapping intervals. Completed W3C lines and distinct session counts alone cannot give an exact per-user in-flight count.

08 / containment, proof and prevention

A practical incident action plan

During impact

Preserve before recovery, if safe

  1. Record UTC time, failing operation, actual HTTP status and selected node.
  2. Capture the same log window on both nodes; collect repeated live samples while the symptom exists.
  3. Capture relevant IIS/HTTPERR, LB, application and database evidence.
  4. If approved, drain the bad member using supported LB controls; verify the healthy node has headroom and account for sticky/InProc sessions.
  5. Restore service under the incident runbook. Do not delay critical recovery just to complete collection.
After stabilization

Prove the cause, then tune

  1. Build a single UTC timeline of errors, request age, queues, dependencies and PID changes.
  2. If requests stall, use approved FREB rules for relevant status codes or slow completed requests; use appropriate dumps/tracing for hangs that never complete.
  3. Capture worker dumps only with approval: they may pause processes, consume disk and contain secrets/customer data.
  4. Fix the supported cause: blocking code, leaked connections, slow dependency, skewed routing or configuration drift.
  5. Repeat a controlled test with representative users, sessions and operations; verify error rate, p95/p99 latency and queue drain on both nodes.
Do not use these as unproven fixes: raising every queue/connection/thread limit, setting unlimited timeouts, disabling rapid-fail protection, adding web-garden workers or scheduling repeated IIS restarts. These can mask failures, increase latency, overload SQL, break session behavior or erase evidence. Adding ports/hosting instances alone does not remove a shared dependency bottleneck.

Measurable acceptance criteria

Agree business-appropriate targets before testing; none were supplied. Demonstrate no unexplained busy responses during the agreed peak-load and soak windows, latency within the agreed p95/p99 SLO, no steadily growing queues or resource leaks, balanced work consistent with the LB policy, successful safe node drain/failover, and correct login/session behavior across nodes. Capture expected versus observed values, rather than only "CPU normal."

Evidence checklist for the next incident

Checklist state is local to this open page and is not saved. Print to retain a completed copy. The inventory's Windows Server 2012 entry also warrants a separate support/ESU, patching and migration review; it is not evidence that OS age caused this incident.

RCA handoff format

Impact → UTC timeline → rejection layer → observed bottleneck → causal evidence → contributing factors → recovery → permanent correction → validation results → owner / due date. Distinguish the primary cause from the reason only one node was affected and from any failure to drain or fail over.
