Technical Design Document

HFLMS Load Balancing & Hosting Architecture

Incident context, current deployment, and two application-hosting scale-out options.

1

Current issue and findings

HFLMS is behind a Citrix load balancer, but a request that receives an HTTP 503 Service Unavailable is not being routed away from the unhealthy application server. The load balancer's available configuration does not support using the HTTP response code as the health/routing criterion required for this behavior.

2 incidentsApplication service interruptions were observed.
8 minutesDuration of the first interruption; a forced IIS restart was required.
2 minutesDuration of the second interruption.
Operational finding: RAM and worker-process utilization were reported as normal and below their thresholds during the issue. The observed symptoms therefore were not accompanied by high utilization of these monitored resources.
Design constraint: Based on the current findings, Citrix cannot be configured to make this routing decision from the application's HTTP response code. The options below increase hosting distribution; they do not, by themselves, change the load balancer's health-check capability.
2

Current architecture

Two IIS application servers host two application hosting instances in total. Traffic to the application servers is load balanced. Notification has two dedicated servers; SMS and database functions each have one dedicated server.

Proposed architectures

Both options increase the number of application hosting instances available to the load balancer. Notification, SMS, and database servers remain as in the current architecture.

Option 1 — Increase to 4 hostings

Keep 2 application servers; configure 2 IIS hostings per server and load balance across all 4.

Implementation considerations

  • Confirm that the Citrix service group can target each hosting instance and that health checks reflect the hosting's actual ability to serve requests.
  • Document the IIS bindings, ports, certificates, application configuration, and deployment steps for each additional hosting.
  • Validate session/state handling and any shared dependencies before distributing requests across more hosting instances.
  • Load-test the selected option and monitor per-hosting availability, HTTP 503 responses, IIS worker processes, memory, and server health.
  • Agree on the selection between the two options based on capacity, availability targets, infrastructure cost, and operational support.
